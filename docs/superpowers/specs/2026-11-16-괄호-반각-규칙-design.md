# 괄호 （ ）도 반각으로 쓰는 형식 규칙

## 왜

형식 규칙 "문장부호·숫자·영문을 반각으로"는 괄호를 예외로 둔다. 모델에게 가는 글이 "괄호는 원문에 쓰인 글자 그대로 둔다"고 하고, 프로그램의 반각 변환(`toHalfWidth`)도 `（ ）`를 건드리지 않는다. 사용자는 한국어 표기대로 반각 `( )`를 원하는데, 번역이 반각으로 쓰면 검수가 "전각 괄호를 반각으로 바꿨다"는 의견을 내고, 그 의견을 받으면 전각으로 되돌아간다.

## 목표

- 사용자가 켜면 `（ ）`를 반각 `( )`로 쓴다. 번역, 검수, 내보내기 지침이 모두 같은 말을 한다.
- 켠 뒤에는 검수가 괄호의 전각·반각 차이를 문제로 돌려주지 않는다.

## 하지 않는 것

- `「 」 『 』 【 】`는 반각 글자가 없으므로 그대로 둔다. `［ ］ ｛ ｝ ＼ ％`도 지금처럼 둔다.
- 이미 저장된 번역을 한꺼번에 바꾸지 않는다. 이미 쌓인 검수 의견도 지우지 않는다.
- 판단 필요(needsDecision) 항목과 keep 이 있는 항목은 지금처럼 변환하지 않는다.

## 피해야 할 것

- 기존 프로젝트의 동작이 말없이 바뀌는 것. 규칙 값이 없는 기존 `glossary.json` 은 꺼짐으로 읽는다.
- 괄호를 보고 동작하는 플러그인이 있는 게임에서 끌 방법이 없는 것.

## 따져 본 방법

1. **따로 켜고 끄는 규칙을 더한다 (선택)**: 게임마다 고를 수 있고 기존 프로젝트가 안 바뀐다.
2. 기존 반각 규칙에 괄호를 그냥 포함한다: 칸이 안 늘지만, 기존 프로젝트의 번역 결과가 말없이 달라지고 괄호를 읽는 플러그인이 있는 게임에서 피할 길이 없다.
3. 검수 지침만 고쳐 괄호 차이를 무시하게 한다: 검수 의견은 사라지지만 번역 결과가 전각·반각으로 섞인 채 남는다.

사용자가 1번을 골랐다.

## 설계

- 형식 규칙에 `halfWidthBrackets: boolean` 을 더한다(`ProjectRules`). 새 프로젝트 기본값은 켜짐, 값이 없는 기존 파일은 꺼짐.
- 용어집 화면의 형식 규칙에 "괄호 （ ）도 반각으로" 칸을 더한다. "문장부호·숫자·영문을 반각으로"가 꺼져 있으면 이 칸은 쓸 수 없다.
- `toHalfWidth` 에 괄호도 바꿀지 정하는 선택 인자를 더한다(이름은 그대로, 인자만 추가). 제어문자가 달라지면 원문을 그대로 돌려주는 지금의 안전장치는 유지한다.
- 번역 작업과 검수 작업이 결과를 반각으로 바꿀 때 이 규칙을 넘긴다.
- 모델에게 가는 형식 규칙 문장(번역·검수·내보내기)을 규칙에 따라 바꾼다. 켜짐: "（ ）는 반각 ( )로 쓴다. 「 」 『 』 【 】 는 원문 글자 그대로 둔다." 꺼짐: 지금 문장 그대로.
- `CHANGELOG.md` 와 `README.md` 의 형식 규칙 설명에 한 줄씩 더한다.

## 만드는 사람이 정할 것 (Claude의 선택으로 표시)

- 형식 검사기(`check/format`)가 괄호 글자를 원문과 비교하는지 확인하고, 비교한다면 이 규칙이 켜졌을 때 전각·반각을 같은 것으로 본다.
- 규칙 이름과 인자 모양의 세부.

## 확인

- 시험: 변환 함수(켜짐·꺼짐, 제어문자 안전장치), 규칙 읽기(값 없는 파일은 꺼짐), 지침 문장, 번역·검수 작업의 결과, 화면의 칸.
- 실제 프로젝트에서 켠 뒤 검수를 돌려 괄호 의견이 안 나오는지 사용자가 확인한다.
